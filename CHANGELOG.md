# Changelog

All notable changes to JobNavigator are documented here.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).
Releases are named major.minor ("3.0"); tags before 3.0 carry a `.0` patch (`v2.2.0`).

## [Unreleased]

### Added
- **Levels.fyi apply:** a Levels.fyi job whose own data names no employer link is applied to on Levels.fyi itself, so it counts like LinkedIn Easy Apply (Direct in the Link filter, Open goes to its Levels.fyi page) instead of a Board link.
- **Default cover-letter template:** Settings › Cover letters › **Default template** picks the template for a new letter whose résumé template has no cover-letter version: a blank letter, a letter from Persona, and a letter from a Modern Professional résumé. The list comes from the templates on this install, and the default is Garamond Modern. A generated letter still takes its résumé's template when that template has a cover-letter version. A member reads the owner's choice or its own, as the Cover letters section's policy says. `PATCH /api/settings` rejects a name that is not a cover-letter template on this install with 422; a stored name that the install no longer has gives Garamond Modern.

### Fixed
- **Levels.fyi jobs without text could never be scored:** when the scrape's visit to a job's Levels.fyi page failed, the job had no description, and scoring fell back to the page's visible text: only Levels.fyi's cookie banner and its "Levels.fyi Jobs" blurb, because the posting is drawn by script. The model then answered in prose and every try failed with "not valid JSON". Scoring now reads the description from the page's own data (and saves it on the job), never the banner; a job with no data left on Levels.fyi says there is no text to score. A reply that is not JSON is logged with its first 200 characters.
- **Cover letters from a Modern Professional résumé:** a generated letter took the résumé's template, and `modern` has no cover-letter version, so the letter failed to render ("Unknown template: 'modern'"). A letter now takes the résumé's template only when a cover-letter version exists, and Garamond Modern otherwise. A letter already stored with a template this install does not have renders with Garamond Modern, as a résumé does. Garamond Modern is now the named default for new letters; before, the default was the first template folder, which is `garamond` on an install with the licensed fonts.

## [3.1] — 2026-10-27

3.1 is about the posting behind each job: one job per posting however many sites list it, the employer's own link instead of a board's, and a mark on postings that have closed. It also adds a public demo and opt-in telemetry.

### Added
- **Better deduplication:** the same posting used to reach the feed once per link that spelled it: Greenhouse's hosted board, its embed, a short `grnh.se` link and a company page with `?gh_jid=`; one Workday requisition per location; Jobright, Levels.fyi and the company's own board each with its own link. Each job now gets a posting key read from its link (`greenhouse:8686811002`; over 30 job systems and career sites, including Greenhouse, Lever, Ashby, Workday, iCIMS, Oracle, SmartRecruiters, SuccessFactors, Phenom, TalentBrew, Eightfold, Avature and Uber, and company sites that show an ATS posting under its own number: DocuSign, Bank of America, Brex, Stripe), with ad-tracker links unwrapped and short links followed. A new job that repeats a posting the feed has becomes a **copy** of it, listed on the posting's own row under **Also listed** (by city when the copy is in another one) and linked back from its own panel.
  The same **role** under another id is a copy too: one role listed once per city (LinkedIn, Apple, Axon, Brex), several openings posted the same day (Amazon), a re-post weeks later, or a board listing of the employer's posting. That needs proof from the text, because a title alone proves nothing: the two jobs must have the same company and title (title variants count as one: "Sr" and "Senior", a dash or a comma, word order, "Engineer 2" and "II", requisition numbers), a description the company does not also use under another title, and the same text word for word apart from ids, pay, dates and places (a city named only in the text, "based in our Denver office", is a place too). Replayed over 90 days of the author's jobs (7,756), this hid 130 more copies, and every one was read by hand. It merged none of 21 look-alike pairs that are different roles: two Workday "Senior Product Manager" postings 94% alike but for different products, Apple postings that differ only in naming "legal, finance" or "music", Cisco's "4+" against "6+ years", and Sierra's Spanish- and Portuguese-speaking strategists, who share one text. A listing without a description is never linked by title. When the employer's posting arrives after an untouched listing of it, the listing becomes the copy. A job you saved, applied to or skipped is never hidden, and neither is a job created saved (the extension's save).
  **Settings › Copies of a posting** decides where each kind of copy goes, **Ignored** (the default: out of the feed, listed under Also listed) or **New**: the same posting under another link in the same city, the same role in another city, and the same role reposted under a new id. A copy in a city a role you skipped does not name is not hidden under it: a role skipped in Seattle shows again when it is posted in New York, marked **Skipped in Seattle** (a click opens the skipped one). A run's "+N new" no longer counts copies. Saving another spelling of a known posting from the extension finds the posting. On start, stored jobs are keyed again whenever the link readers change, and untouched copies are linked (on the author's data: 19,287 of 20,856 jobs keyed).
- **Deeper direct-link search:** every job now says whether it reaches the employer's own site: **Direct** (also LinkedIn Easy Apply, where you apply right there) or **Board link** (only a LinkedIn, Indeed, Glassdoor, ZipRecruiter, WhatJobs, Telegram or other board listing is known). The feed has a **Link** filter and a Board link tag in the job's panel, and Open, the o/e keys, the preview, page caching and description fetches use the employer's link whenever there is one (the separate Company site button is gone). Searches show how many of their jobs have a direct link (last 90 days).
  LinkedIn listings from any source (Levels.fyi, Jobright, JobSpy) are looked up through the **mock account** (Settings › LinkedIn): LinkedIn's public page no longer names the employer's link, its logged-in job page does. The lookup runs after every scrape, one request every 2 seconds and up to 200 jobs per run, and asks about each LinkedIn job once; the answer (the employer's link, Easy Apply, or closed) is kept for every account. A run stops when LinkedIn stops answering, and it runs only on a session the mock account signed in, never on yours. A job that gets the employer's link joins the employer's posting the feed already has. Short links and job-ad redirectors (`grnh.se`, `prng.co`, Appcast, Joveo, Recruitics, eQuest) are followed to the posting; one that leads nowhere closes the job instead of being retried forever. Link readers now also cover TalentBrew and Workday links with a language prefix, Phenom ids with `_`, Dayforce without a language, Avature in every form, JazzHR, Jibe, ContactHR, Oracle on a company domain, Greenhouse embed links, and the Visa, Revolut, Capgemini and TCS sites (237 more stored links recognised on the author's data). On the author's data, jobs with a direct link over 90 days: Jobright 87% → 93%, Levels.fyi 29% → 37%, Indeed 12% → 19%, before any LinkedIn lookup.
  Copies can only be proven from text, so more jobs now keep the employer's description: a new Jobright job stores the employer's own text instead of Jobright's AI summary (kept when the fetch fails), a new JobSpy LinkedIn job gets its text from LinkedIn's public job page, and a Greenhouse embed link is read through Greenhouse's job API.
- **Still open?** A job's posting is checked when you open it in the feed and in the résumé and cover-letter editors: through the Greenhouse, Lever and Workday APIs, LinkedIn's public page, or the page itself (a 404, a redirect off the posting, or a closed phrase in the visible text). A closed posting gets a red dot on its feed card and **Closed posting** in its panel and in the editors, with why and when on hover; a bot check or an error counts as unknown, never closed, and a click on the label checks again. Two signals need no check of their own: a listing LinkedIn reports closed or deleted (with an employer link, the employer's page decides), and a posting missing from two full scrapes of its company's board in a row (whole-board APIs only, no failed link, and not a scrape that found under 70% of the last one; a posting that comes back is open again). The feed's last filter, **Posting** (Open / Closed), appears once a closed posting has been found. The application status never changes.
- **Telemetry** (README › Telemetry): the owner chooses once, in a dialog of its own after the Welcome or upgrade notice, **Yes** (preselected) or **Essentials**, and only Save closes it (its "What is sent?" list follows the pick); Settings › Telemetry changes it. Essentials sends once a day, from the server, the version, the account count and the health of each scraper kind, posting kind, AI provider and the LinkedIn lookup (counts as buckets, errors as types); Yes adds page views without ids and named actions, and the address of a failing job board. Browser events go through the install's own server, so Umami never sees a browser, an IP or the install's address; job titles, search terms and anything typed are never sent. Nothing is sent before the choice; `JN_TELEMETRY=off` in `.env` turns it off and locks the choice.
- **Public demo:** [vesaias.github.io/JobNavigator-demo](https://vesaias.github.io/JobNavigator-demo/) runs the real dashboard on sample data in the browser, with no backend. The app has inert hooks for it (`VITE_DEMO=1` sets the base path and swaps the API for an in-browser server from the demo repo); a normal build carries none of the demo.
- **Company site link:** Indeed and ZipRecruiter rows found by a keyword search now keep the employer's own posting (JobSpy's `job_url_direct`; on a live Indeed search, 33 of 40 rows had one), and use it to recognise the same posting from the company's own board.
- **Rename a résumé** (by @volkotyk): in the résumé editor, click the name in the top bar (or ⋯ › Rename) to edit it. Enter or a click outside saves, Escape cancels, and a blank name keeps the old one. Before, the name came only from the create dialog or the imported PDF file name, so two imports of the same file got the same name. The API now rejects a blank or non-string name on `PATCH /api/resumes/{id}` with 400, the same as on create. Job scores already stored under the old name keep that label; a new scoring run uses the new name.

### Fixed
- **The scheduled scrape never ran on a long interval:** the scrape interval counted from when the backend started, so an install restarted more often than its interval (a PC switched off at night, with a 3,500-minute interval) never scraped on schedule, and the LinkedIn lookup that follows a scrape stalled too. The interval now counts from the last scheduled scrape; one that is overdue starts two minutes after the backend does.
- **Uber:** uber.com's careers list moved to jobs.uber.com, and the old list URL redirected to a page that ignored its filters, so a scrape found only "Saved jobs". Uber is now read through jobs.uber.com's search API; a company saved with the old URL keeps its department and city filters. Its chip on Companies has its own colour instead of the generic grey.
- **Navigation is not a job:** job-site links such as "Saved jobs", "Back to search" or "Candidate login", and language-switcher pairs ("German", "Deutsch"), were stored as jobs on some career pages.
- **PDF of a document without some sections:** a résumé or cover letter made through the API or an import without a header (or with no sections at all) failed to render with a 500; the missing sections now render empty.
- **LinkedIn main session survives a rebuild:** its cookie jar lived in `/tmp` and was wiped by every image rebuild; it now sits in `backend/.linkedin_api/` next to the mock account's (a jar still in `/tmp` moves on first use).
- **Stricter host checks** (code scanning): the Still open? check, the short-link check and the demo export match a job's host exactly or as a subdomain (`greenhouse.io`, `lever.co`, `myworkdayjobs.com`, `linkedin.com`), so a look-alike host such as `evilgreenhouse.io` is never treated as one of them. The model catalog's cache no longer hashes API keys with SHA-256 for its key; it keeps them in memory, as the key itself already is.
- **Radio buttons:** the selected dot sat a pixel or two low and left of the centre; it is now drawn in the centre.
- **Score and Tailor errors:** a failed score or tailor from the feed names the server's reason.
- **Workday boards over 2,000 jobs:** Workday's job list never reports or pages past 2,000 results (a bigger board says 2,000, and later pages repeat earlier jobs), so a large board with no filters in its URL silently lost the rest: on NVIDIA's whole board, 727 of 2,724 jobs. A search that reaches 2,000 is now split by one of the board's own filters (job category, location, ...), picking the one that covers every job in the fewest requests, and a part still at 2,000 is split again. Filters already in the company's URL are kept. Boards under 2,000 work as before.
- **Scoring with prompt caching off:** with Settings › Scoring behavior › prompt caching switched off, scoring sent the model only the job description: the résumés, the rubric and the answer format went out with the cache block. They are now in the prompt itself whenever caching is off.
- **LinkedIn Remote** (by @volkotyk): LinkedIn ignores its remote filter (`f_WT=2`) without login: on 2026-10-22 the guest endpoint and the public search page returned the same rows with and without it. The Remote field and the Apify LinkedIn board hint said that Remote worked on LinkedIn; they now say that Indeed, Glassdoor and Google apply it and LinkedIn does not. A Remote-only Apify LinkedIn search now drops the rows that the posting calls hybrid or on-site; rows with no stated arrangement stay. Apify still bills every fetched row, so this filter does not lower the cost.
- **An override never borrows a model of another provider:** an override set to a provider other than the Primary's but with no model of its own used to send the Primary's model name (a Claude model to OpenAI) and retry the error four times. It now inherits the Primary's model only on the same provider; otherwise an API provider fails at once with "No model picked for OpenAI — pick one in Settings › Models" (the subscription CLIs keep their own default).
- **Local model addresses visible to the owner:** with several accounts the LM Studio and Ollama address rows show for the owner even when none of the owner's own slots uses them, since a member's slots may, and only the owner can set the address.
- **Downloads have the last edit and say why they failed:** a résumé or cover-letter download first sends an edit the autosave still owes, so the file has the last keystroke; a failed download names the server's reason ("Could not download the PDF — …") instead of a bare error.
- **Download file names:** a name built from the header name, résumé name or company keeps no `/`, `\`, `..` or reserved characters and is cut to 120 characters.
- **Résumé size:** a résumé's JSON must be an object of at most 512 KB (400 otherwise), on create and on save; a huge paste made every preview render take 20 s.
- **OpenCode Go usage limit:** a 429 or a usage-limit reply goes straight to the fallback model instead of being retried four times, like the subscription CLIs.
- **Ollama errors:** an error from Ollama no longer carries the server address (the owner's setting) into a member's toasts and LLM log; it names the HTTP status or "not reachable".
- **Autofill streaming logged:** an answer the extension streams is logged in the LLM log like a non-streamed one (its token counts are 0: a stream carries no usage).
- **Apify 402:** the error names Apify's own reason (a rented actor without a subscription, a platform limit, a charge cap) instead of always "no credit left".
- **Copying an Apify search:** the copy dialog and a toast say the copy is paused, instead of "runs at the next scheduled pass".
- **CI runs the frontend checks:** Vitest and the style lint run on every push and pull request.
- **Search modes checked by the API:** creating or switching a search to an unknown mode, or to one of the two built-in extension modes, is refused (400); a built-in extension search keeps its mode. `sources` is checked against the mode (JobSpy boards, LinkedIn collections, Apify boards) and is empty for a mode that takes none, so a Levels.fyi or freehire search no longer stores JobSpy's default boards, and a search switched from Apify back to JobSpy gets JobSpy's boards instead of keeping Apify's (whose next run failed). A manual run of a Levels.fyi search without a URL or an Apify search without a term or board now says what is missing.
- **Levels.fyi job links:** since 2026-10-09 levels.fyi job ids are letters and digits (`jobId=2ci7r6weraiqb`) instead of 18 digits. The scraper kept only the leading digits, so a job was stored as `jobId=2`: its link opened a 404 page, scoring read that page and failed on every run, and jobs whose ids began with the same digits were merged into one. The scraper now keeps the whole id.
- **Antigravity CLI expired login** (by @volkotyk): `agy` 1.3.3 and later reports an expired or revoked token as "Authentication expired. Please log back in." The adapter now treats it as "not logged in": the call goes straight to the fallback provider and the error names the login command. Before, it was a plain failure that the backend retried.
- **Antigravity CLI on -high models** (by @volkotyk): one résumé tailoring on `gemini-3.8-flash-high` took 194 to 368 s over three runs, so the 300 s CLI limit cut off answers that were on the way. Two of the three runs also tried `run_command ls` and `read_file` in the empty workdir first: the CLI offers its 60 tools whatever the deny list says, the deny list blocked the calls, and the model then thought longer. The message to `agy` now tells the agent to answer from the text and call no tool; three runs after the change made no tool call and took 86 to 300 s. Antigravity also gets a limit of its own, 450 s, which stays under Caddy's 480 s read timeout for the PDF import; Codex and Claude Code keep 300 s. The deny list and the check of `agy`'s log stay as they are. Settings › Models says that -high models can think for minutes on these jobs; -medium did the same tailoring in 13 to 39 s.
- **LLM log for a cancelled call** (by @volkotyk): a call cut off mid-flight (container stopped, request gone) was logged as a success with 0 tokens, because `asyncio.CancelledError` is not an `Exception`. It is now logged as a failure with the error "cancelled".
- **Subscription CLI timeouts are not retried** (by @volkotyk): when Codex CLI, Claude Code or Antigravity CLI passed its time limit, `call_llm` ran the same prompt on the same model three more times. One stuck scoring or PDF import then took 4 × 300 s and held a CLI slot (two per CLI) the whole time. A timeout now goes straight to the fallback model, or fails at once when there is no fallback. The time limits stay as they are; other errors still get four attempts.

### Changed
- **Settings, tidied:** the posting zoom switch moved into Display (the separate Feed section is gone); a member sees the sections in the owner's order; an install with one account shows no scope tags, and the owner's own sections no longer say "Per account"; the Claude Code token, the CLI logins and the LM Studio / Ollama addresses say what an empty box does, with the rest under (i).
- **Ghosted and Withdrawn** are gone from the application status lists and filters (nothing sets them any more).
- **Wording:** a search's option reads "Skip my active companies" and says which companies; a Test preview job that had no text to check against your exclusion phrases reads "posting body text check was skipped".
- **Two LinkedIn sessions, each with its own Sign in:** Settings › LinkedIn has a **Main account** (your own; LinkedIn Personal searches use its session) and a **Mock account** (the extension import and the employer-link lookup use its session), each with a session row and a **Sign in** button that handles LinkedIn's emailed PIN. Before, one "Session cookie" row and a "Use a mock account" switch decided which account a refresh signed in, and the main account's session had no sign-in at all, so LinkedIn Personal stalled at LinkedIn's PIN check. The switch is gone: with a mock account set the import uses the mock session, without one the main session. Each sign-in records which account the session holds; the employer-link lookup runs only on a session the mock account signed in, never on yours. `python -m backend.refresh_linkedin_session --session main|mock` does the same from the command line.
- **JobSpy 1.4.1** (from 1.3.0): ZipRecruiter works again after its site changed, LinkedIn reads pay from the description on US searches, and a failed board is read from JobSpy's own report instead of its log. Indeed, Glassdoor and ZipRecruiter now tag remote jobs from the board's own data, so their remote tag is used. JobSpy 1.4 dropped ten countries that have no Indeed site (Bulgaria, Croatia, Cyprus, Estonia, Latvia, Lithuania, Malta, Slovakia, Slovenia, Bangladesh): a search saved with one of them now says so instead of failing.
- **Job scores are stored by résumé id:** a job's scores, its full report and its best résumé used to be stored under the résumé's *name*, which the model answered with. Renaming a résumé left old scores under the old name (one job could show both), two résumés with one name overwrote each other's scores, and a résumé named "Tailored" would have collided with the tailored copy's key. Scores are now stored by résumé id and shown under the résumé's current name everywhere (Jobs, Applications, Stats, Telegram alerts); a rename shows at once, and a deleted résumé's old scores keep the name it had when they were scored. Two résumés with one name are scored as "PM" and "PM (2)". "Tailored" and "Persona" keep their own keys. Existing scores are converted on the first start: a name maps to the account's base résumé of that name (the newest when two share it; the log says so); scores under the name of a résumé that no longer exists stay under that name.
- **One API key per provider:** the API key box under the Primary model and on each override now holds the key of the slot's *provider* (`anthropic_api_key`, `openai_api_key`, `openrouter_api_key`, `opencode_api_key`). Every slot on Claude API uses the one Anthropic key; switching a slot to OpenAI shows the OpenAI key, and switching back brings the Anthropic key back, so nothing is re-pasted or sent to the wrong provider. Switching an override off keeps the provider's key. Existing keys move over on the first start: each slot's key goes to the provider that slot was using; when one provider had different keys the Primary's wins and the log names the others; a key in a slot with no provider (a switched-off override) is not moved. The model picker finds a key set while only Scoring used that provider. OpenRouter now also falls back to `OPENROUTER_API_KEY` in `.env`. The old per-slot keys stay in the database for one release, so a downgrade still finds them, but keys pasted after the upgrade have to be pasted again after a downgrade.
- **One table of search modes:** what each mode is (label, scraper module, shared or per-account fetch, Test in the background, country check, board list, what it needs before it runs, paid) lives in `backend/scraper/search_modes.py`, and the dashboard's copy in `frontend/src/searchModes.js`; about 25 hand-kept lists read them instead. A test fails when the two tables differ or a new hand-written mode list appears. Adding a source is one entry in each plus its module.
- **Scrapes run one at a time:** a new setting, Scheduler › Scrapes at once (`scrape_max_concurrent`, 1 or 2, default 1), gates every scrape: Run all, one company, one search and the scheduled scrape. A scrape started while another runs is accepted and waits its turn; Companies, Searches and Stats show it as "Waiting" until it starts, and its run time is counted from then. Before, two accounts' Run alls (or a Run all and a company scrape) ran side by side, each with its own Chromium. A manual scrape started while the scheduled one runs is still refused, as before.
- **A recent fetch is reused:** a board or career page another run fetched less than 10 minutes ago (or is fetching now) is not downloaded again when the target is the same and the earlier fetch asked for at least as many results and as old a window. Two accounts' Run alls back to back, or a Run all followed by the scheduled scrape, fetch each shared target once. Each account still filters, dedups and stores its own rows; a failed or empty fetch, Apify and the per-account sources (LinkedIn personal, Jobright) are never reused, and a board's throttle stop lasts one run.
- **Frontend builds on Node 24:** the frontend image and the Vitest runner use `node:24-alpine`. Its npm 11 resolves vitest 4's optional peers by itself, so the `overrides` entry that npm 10 needed is gone from `package.json`; the tree still has one Vite (6.4).
- **Prebuilt images for ARM** (by @volkotyk): the backend and frontend images are published for `linux/arm64` as well as `linux/amd64`, so an ARM host (Apple Silicon, Raspberry Pi, RK35xx boards) runs `docker compose pull` instead of building Chromium from source. The arm64 build runs under QEMU in the same job, so the backend image takes about 12 minutes on a cold cache.
- **Antigravity CLI 1.4.3 in the backend image** (by @volkotyk): `AGY_VERSION` is now 1.4.3, so the next `docker compose build backend` reinstalls the CLI instead of keeping a cached 1.2.13 layer. Flags, the deny list and the result event were checked against 1.4.3.

## [3.0] — 2026-10-17

JobNavigator becomes a household install: one server, up to five accounts, each with its own data. An existing install keeps everything it has: the data becomes the owner's account, and with one account the dashboard looks and behaves as before.

### Upgrading from 2.x
1. **Back up first.** The upgrade migrates the database in place and there is no way back to 2.x except a restore. 3.0 also dumps the database to `backups/pre_upgrade_2.x_to_3.0_<timestamp>.sql` on its first boot, before migrating, and does not start if that dump fails. With 2.x still running: `docker compose exec -T db sh -c 'pg_dump -U $POSTGRES_USER $POSTGRES_DB' > backups/pre-3.0.sql` (restore command in `docs/GETTING-STARTED.md` › Scheduling, backups, upkeep).
2. **Update:** `git pull`, then `docker compose pull && docker compose up -d` (prebuilt images) or `docker compose up --build -d`. If `.env` pins `JN_IMAGE_TAG`, set it to `3.0`. `git pull` alone is not enough — the images must be pulled or rebuilt: the compose file mounts the new backend code into whatever image is there, and a 2.x image lacks packages 3.0 needs (the dashboard and the backend log then say so).
3. **First boot migrates by itself:** it adds an account column to every owned table, creates the owner account (named after your Persona, else "Owner") and gives it every existing job, application, résumé, cover letter, search, company, Persona and log. Settings you already have stay install values and become the owner's (a member later inherits them or keeps its own, section by section); settings new in 3.0 are seeded with their defaults, and existing values are not touched. The install password (dashboard API key), Telegram bot and chat, and `GMAIL_REFRESH_TOKEN` keep working for the owner.
4. **Reload the extension** (`chrome://extensions` › reload): it becomes 3.0; its permissions and URL patterns are unchanged, so no reinstall is needed.
5. **Optional:** to connect Gmail from Settings instead of `.env`, add `<your dashboard address>/api/gmail/callback` as an authorized redirect URI in the OAuth client. To add people, Settings › Accounts › **+ Add account**.

### Added
- **Household accounts:** one owner plus up to four members. The install password still opens the install; with two or more accounts a picker follows, and any account, the owner's included, can carry an optional 4-digit PIN (the owner's PIN opens any member; five wrong tries wait 30 s; an account without one opens in one click). The choice is remembered per browser (`Ctrl + Shift + 1–5` switches, `⌃⇧1–5` on a Mac; a switch saves pending edits to the old account first, and the browser's other tabs show a "switched in another tab" notice and stop saving until reloaded). With one account the only new thing is Settings › Accounts at the top (your own row and **+ Add account**).
- **Separate data per account:** jobs, searches, companies, applications, interviews, résumés, cover letters, Persona, tracer links, activity and LLM logs, runs and scrape logs. Every query is scoped centrally, background work (digest, auto-reject, cleanup, e-mail check, scoring) runs once per account, and a two-account leak test walks every API route.
- **Shared scraping:** two accounts that watch the same company page or run the same keyword search cause one fetch. Each account then ingests the postings through its own filters, excludes, dedup, H-1B and salary checks and auto-scoring. The shortest interval wins; results and age limits are trimmed per account.
- **Settings inherit or own, per section:** the owner decides for each member whether a section (models, notifications, filters, …) follows the owner's values or is the member's own. The owner sets a member's policies from Settings › Accounts: the **Edit policies** switch on the member's row turns on an Inherit / Own control on each section, and it is off again on every load. A member sees a scope tag on each section (Display, which is per browser anyway, carries none), the member's nav groups yours and shared sections, and owner-only sections sit behind a lock card with an inline owner-PIN unlock (15 minutes; a plain Unlock button when the owner has no PIN, which makes it a privacy latch only).
- **Per-account credentials and logins:** provider API keys follow the section policy; Claude Code (token), Codex (`CODEX_HOME`) and Antigravity (state dir) get a login per account (`backend/scripts/cli_login.py` prints the command); LinkedIn, Jobright and Levels sessions and cookie files are per account.
- **Telegram per account:** the household bot routes by chat (link with a 6-digit code and `/start <code>`), or a member brings their own bot with its own webhook. Inline buttons act only on the chat's account; system alerts go to the owner.
- **Gmail per account:** connect from Settings with Google's consent screen instead of `.env` tokens (the OAuth client stays in `.env`; add `http://localhost/api/gmail/callback` as an authorized redirect URI). An existing `GMAIL_REFRESH_TOKEN` keeps working for the owner.

- **Location menu** lists the busiest country first and its regions and cities by count; a city that is also its region's name is one entry.
- **Amazon handler:** the search page's `country[]` filter is translated to the key the JSON feed honours (`normalized_country_code[]`), so a US-filtered URL no longer returns the world.
- **Location parser hardened on a corpus of 642 real posting strings** (checked in as a golden-file test): lists, foreign city-region-country triples, hyphen triples, metro names, addresses, office labels, "Washington State", Georgia the country, a city gazetteer for "City, CA"; a held-out code must fit exactly one candidate country, so a cross-border posting never files a US city under Canada.
- **Codex CLI provider** (by @funstuie-bit, #8): use a ChatGPT subscription for scoring, tailoring, letters, autofill and email through `codex exec`. One-time `docker compose exec backend codex login --device-auth`; token usage is logged, cost counts as $0.
- Follow-up hardening: a login pre-check that names the fix instead of a 15-second 401 storm, `turn.failed` surfaced as the error (a usage-limit hit fails over to the fallback provider without retrying), a 5-minute timeout on both subscription CLIs, and at most two concurrent Codex processes on the shared login file.

- **Applications: bulk actions**, the Jobs feed's exactly — ⌘/Ctrl-click picks rows, ⇧-click takes a range, and a floating bar moves the whole selection to Applied, Interview, Offer or Rejected (with an undo toast that puts every row back to the stage it came from). A stage the selection is already in is dimmed and does nothing. New `POST /api/applications/bulk-update` and `/bulk-delete`.
- **Add a job to the feed from the Log modal** (by @volkotyk, #9): the Applications › Log modal's Status now offers New and Saved beside the stages; those write a feed job only (`POST /jobs/manual`, deduplicated against existing rows), and a ✦ Tailor trigger beside each base résumé saves the row and starts a tailored copy.
- **Applications: undo on the stage stepper.** Moving one application to another stage shows the same undo toast the bulk bar has; an undo drops the transition it reverses instead of logging a new one, so the Stats funnel stays honest.
- **Getting-started guide** (`docs/GETTING-STARTED.md`): install, provider choice including the Claude Code and Codex CLI subscription logins from inside the container, résumés and Persona, companies, searches, the feed, the extension, Telegram and Gmail. README Quick Start reworked around it.
- **Version** in the Settings colophon comes from the build (the backend's is noted when it differs) and is on `/health`.

### Changed
- **Status filter:** picking nothing shows every status, like the other filters, and the pill's ✕ clears to Any; a browser with no saved filters starts on New.
- **Feed row:** the third line never wraps — salary · arrangement · H-1B · age; when space runs out the H-1B verdict gives way first and the age stays whole. The company name keeps its width; the location line shrinks.
- **Selection:** the first ⌘/Ctrl- or ⇧-click includes the row that is already open, on the Feed and in Applications. The bulk bar's buttons hover in the rail's own tones (Windows 98 gets a raised strip with bevel buttons); the Applications bar has no Delete.
- **Extension** 2.1, same code as 2.0.

### Fixed
- **Auto-scoring and the daily digest on fresh installs** (by @volkotyk, #11): `cv_scores` is created as `json` on a new database, and comparing it with a `jsonb` literal aborted every auto-score pass after a scrape and every digest; both compare as text now. Run errors no longer store or return the failed SQL statement and its parameters.
- **Cover letters for hand-logged jobs** (by @volkotyk, #7): a job logged from Applications has no stored description, and generation refused it. The letter worker now resolves the text the way tailoring does (description, then a live fetch saved to the job, then the cached page); logging an application queues that fetch; the description backfill covers applied jobs.
- **Feed paging under a filter:** a filter change starts a new load generation, so a page still in flight from the old filter is dropped instead of appended; every job sort carries an id tiebreak so pages never overlap.
- **Handler filters:** Greenhouse tolerates spaces in department and office ids and logs what it discards; Rippling compares country and region through the parser; Ashby reads secondary locations; Lever quotes filter values.
- **Cairo and Bengaluru in a US feed:** the Amazon handler honoured no country filter, and country-first strings ("IN, KA, Bengaluru") read as Indiana; both fixed and existing rows re-parsed.
- **Select boxes** in Paper and Green Paper no longer clip descenders.
