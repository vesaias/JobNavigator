# T3 — Visual review across themes

Scope per `ROUND4-PLAN.md`: 13 routes × 5 themes (Default, Board, Cobalt, SaaS, Win98) ×
light/dark × 1440/1024, reviewed at 1440 (130 screenshots); Firefox + Chromium spot
check for Default; PDFs (résumé × 8 templates, one tailored copy, one cover letter)
page-by-page; a WCAG contrast table per theme; the Cobalt/SaaS sameness list and the
Win98 depth-delta list as design-brief inputs. Screenshots captured with
`v2-testing/tools/shots.py <stage> --theme <name>` against the paused live stack
(scheduler off for the capture window, restored after) and live under
`v2-testing/artifacts/round4/t3/<theme>/`. This pass does not repeat verdicts already
recorded in `v2-testing/round-design/proof-skins-A.md` (static token/contrast audit)
and `proof-skins-B.md` (visual review of Cobalt/SaaS/Win98 against the default
baseline) — only what is new, changed since, or was missed there (including a
dedicated fresh pass on the Default and Board themes, neither of which had a
standalone review before this round).

WebKit could not be tested: the backend container's Debian trixie base has no
compatible package for the exact old sonames (`libicudata.so.66`, `libjpeg.so.8`, …)
Playwright's WebKit 2092 build (an ubuntu20.04 fallback, since this OS isn't
officially supported) requires; Firefox's dependencies installed cleanly via
Debian-trixie-equivalent package names and it launched and rendered normally.

## Findings

### R4-T3-01 — PDF: last section/line orphaned onto an otherwise-blank second page

**Severity**: P1 · **Theme**: n/a (PDF export, all themes) · **Route**: Résumé PDF
export (`GET /api/resumes/{id}/pdf`) · **What**: fetched the base "PM" résumé through
all 8 templates plus its "Nomura" tailored copy. 6/8 templates (garamond,
garamond_alt, helvetica, montserrat, palatino, raleway) fit the identical content on
one page with comfortable bottom margin. Two templates — **inter** and
**traditional** — spill onto a near-blank second page: `inter` orphans just the final
line ("Bachelor of Science, Information Systems"); `traditional` orphans the entire
Education section (both entries) even though page 1 still has ~40% headroom below the
last visible line ("Languages: …"). The **tailored copy** (garamond — the template
that fits cleanly for the base résumé) also spills, orphaning the same lone last line,
because tailoring lengthens a few bullets just enough to cross the per-template page
budget. In every case the second page is otherwise empty (a single line or a short
section sitting alone). No orphan/widow control, no auto-shrink, and no
"keep the last section's heading with its first line" rule protects against this —
the renderer just lets the flow cross the page boundary wherever it falls.
**Screenshots**: `scratchpad/pdfs/png/base_inter_p1.png` + `_p2.png`,
`base_traditional_p1.png` + `_p2.png`, `tailored_p1.png` + `_p2.png` (rendered via
PyMuPDF from PDFs fetched through the live API; not copied into the repo — regenerate
via the API calls in the method note below if needed).
**Method**: `GET /api/resumes/{base_id}/pdf?template=<name>` for all 8 templates,
`GET /api/resumes/{tailored_id}/pdf`, `GET /api/cover-letters/{id}/pdf`; rendered to
PNG with PyMuPDF (`fitz`) at 2x scale.
**Status**: needs decision

### R4-T3-02 — Win98: `.v2-scroll` custom scrollbar is not reskinned in any theme

**Severity**: P2 · **Theme**: Win98 (also present, less jarring, in every other theme)
· **Route**: any scrollable list/pane (Feed job list, Feed detail pane, Persona
sections, Settings nav) · **Appearance**: light+dark · **What**:
`frontend/src/v2/theme.css` lines 1105-1107 hard-code the app's custom scrollbar
thumb as a theme-independent 9px-wide, fully rounded (`border-radius:99px`) pill in
`--muted` on `--bg`, with no `data-theme="win98"` override. Win98's own geometry
contract is "0 radius everywhere... no exceptions found" (confirmed by
`proof-skins-B.md`'s corner-radius check) and the reference implementation
(jdan/98.css) uses a chunky 16-17px square scrollbar with a beveled 3D thumb, a
dithered track, and functional arrow buttons — one of the most recognizable Win98
signatures. A thin modern rounded scrollbar thumb sitting inside an otherwise flat,
square, bevelled Win98 window is a visible, contradictory paint. Not clipped or
unreadable, but a clear geometry-contract miss once bevels are fixed per the existing
P2 in `proof-skins-B.md`.
**Status**: needs decision

### R4-T3-03 — Win98: hyperlink ink uses the navy accent, not the classic bright link blue

**Severity**: P3 · **Theme**: Win98 · **What**: `--link-ink`/`--link-ink-hover` are not
overridden in the win98 theme block, so they fall through to `var(--accent)` = `#000080`
(the same navy used for the title bar and selection fill). Genuine Windows 98 (and
jdan/98.css's `--link-blue`) uses a brighter `#0000ff` for hyperlinks, visually
distinct from the navy title bar/selection. Low-impact since the app has few bare
inline text links, but a legibility/authenticity nit worth a token (`--link-ink:#0000ff`
in the win98 block) if the depth pass goes ahead.
**Status**: needs decision

### R4-T3-04 — Cross-browser (Chromium vs Firefox), Default theme: clean

**Severity**: — (informational) · **What**: captured all 13 routes at 1440/light in
both Chromium and Firefox (`v2-testing/artifacts/round4/t3/browsers/`). Compared
pixel crops of buttons (pill radius), toggle switches, dropdown carets, Recharts SVG
charts (Stats), and the Résumé/Persona form-field layouts. No material rendering
differences: button pill radius, switch track/knob colors, and chart rendering are
pixel-consistent; text reflow differs by a word here and there (expected sub-pixel
font-metric variance, e.g. one Persona bullet wraps a word earlier in Firefox) but no
clipping or broken layout in either engine. WebKit not tested — see the header note.
**Status**: closed (no action — recorded for completeness)

## Win98 theme

Reviewed all 26 screenshots twice — once directly (pixel-cropping and channel-level
border scans) and once via a dedicated agent pass that additionally cross-referenced
the current source (`ui.jsx`, `theme.css`, and per-screen files at HEAD `61d00ef`) —
to verify each of the four defects `proof-skins-B.md` logged and commit `18a775a`
("Skins proof fixes: win98 selected-row ink, bevels scoped to win98, label
case/tracking scale token, engraved disabled ink…") claimed to fix. Two are cleanly
fixed; the other two are fixed at the primitive level but leave several hand-rolled
call sites that never adopted the primitive, still showing the original defect.

- **Row-selection ink — VERIFIED FIXED.** Feed's selected row (light: navy `#000080`
  fill; dark: `rgb(43,58,92)` = `#2b3a5c`) shows white title/company/meta text in
  both modes — pixel-sampled directly, no black-on-navy anywhere.
- **Disabled button ink — VERIFIED FIXED.** Cover Letters' empty-form "Generate cover
  letter" button: ink and background are the *same* `rgb(128,128,128)`, legible only
  via a 1px near-white emboss offset on each glyph — the authentic win98
  "ghost/engraved" disabled look, pixel-confirmed, not a flat muted-grey disable.
- **Bevels — fixed at the primitive level, several hand-rolled controls never got the
  hook.** `Pill`, `Select`, and `Input`/`Textarea` *do* correctly bevel (confirmed on
  Companies'/Feed's search boxes, Settings' dropdowns, Persona's fields, Run/Test
  pills, the Applied/Interview/Offer/Rejected segmented control, and Settings'
  "Manage…" button — light top/left, dark bottom/right, both modes). But channel-level
  border scans of Feed's action buttons show the shared `Button` primitive is not
  bevelled at all: the secondary "Open" and the "…" icon button get a **flat, single
  uniform `#404040` stroke** on every edge (scanned row: `(192,192,192)` pane → sharp
  jump straight to `(64,64,64)` → `(192,192,192)` interior, identical value on both the
  left and right edge), and the primary "Tailor résumé" button has **no border pixel
  at all** — the fill jumps directly from the pane grey to solid navy with zero
  transition pixels, not even a flat stroke. Two more hand-rolled sites bypass the
  bevelled primitives entirely: Settings' own "Search settings…" field (`Settings.jsx`
  hand-rolls a `.v2-fieldwrap` div with a plain `border:1px solid var(--edge)` instead
  of using `SearchInput`) and the PDF-preview `Template`/`Paper` `ToolbarTrigger`
  pickers (excluded from the `v2-inset` hook by the primitive's own code comment, on
  every theme, not just win98). **R4-T3-09, P2, needs decision**: bevel the `Button`
  primitive (all variants) and route Settings' search field through `SearchInput`.
- **Label case/tracking — fixed in the four spots `proof-skins-B.md` sampled, the same
  hardcoded-uppercase pattern persists unfixed in at least four more.** Sentence case
  confirmed correct now on: the rail's group headers ("Find"/"Apply"/"You"), the
  Résumé Base/Tailored badge, and the toast-lab kind labels. Still forced uppercase,
  each for its own distinct code reason: **Settings' left-nav group headers**
  ("GENERAL"/"AI"/"PIPELINE"/"INTEGRATIONS"/"SYSTEM" — `Settings.jsx` passes literal
  uppercase *strings* like `'GENERAL'` to `Label`, so `--label-case:none` has nothing
  to lowercase); **the Cover Letters stage badge** ("DRAFT" — `CoverLetterEditor.jsx`
  calls `.toUpperCase()` on the stage value; the fix commit updated this span's
  tracking/case *CSS* but never touched the string transform feeding it, so the fix
  is cosmetically applied but structurally inert); **Feed's unscored-job "SCORE" chip**
  (`JobFeed.jsx` hardcodes inline `textTransform:'uppercase'`, never reads
  `--label-case`); and **Stats' LLM-cost table head** ("PURPOSE MODEL CALLS COST
  CACHE" — `Stats.jsx` hand-rolls a `COL` style object with its own
  `textTransform:'uppercase'` instead of using the `TableHead` primitive, which the
  *same page*'s "Schedules" table two cards below uses correctly and renders in
  proper sentence case). **R4-T3-08, P2, needs decision**: this is a systemic pattern
  (hardcoded strings/inline styles bypassing the token) worth one sweep across the
  four sites, not four one-off patches.

**R4-T3-10 — Win98 dark mode: selected-row background barely distinguishable from
the unselected desktop tone.** Severity P3 · `v2_feed` dark · pixel-sampled: selected
row `rgb(43,58,92)` vs. unselected-row/desktop `rgb(31,43,58)` — both dark
navy-adjacent tones with a small luminance delta. Text is still legible (white-on-navy,
per the fix above), but at a glance it's hard to tell which row is active in dark
mode, unlike light mode's much higher-contrast teal-desktop vs. navy-selection split.
**Status**: needs decision

Confirmed clean: ASCII ScoreRing renders correctly with no clipping/wrapping in
every place it appears (Feed rows, Feed detail, Résumé tailored-copy header — "40
[...]"/"77 [...]"); zero corner radius holds everywhere checked (cards, rows, pills,
buttons, modals, switches, table strips); the teal(light)/navy(dark) desktop ground
shows correctly behind the grey window chrome on every list-style route (the
full-bleed two-pane detail/editor routes have no gutter by layout design, not a lost
desktop); the rail base stays grey with only the active item's own tile filling navy;
the Switch primitive is correctly reskinned as a flat square (track+knob, no radius)
with win98's own navy-on/grey-off colors rather than inheriting another theme's pill
shape; no regression to any of this from the later hover/pressed-state commit — win98
already carries its own `--input-border-hover:var(--bevel-inset-color)` override to
avoid an invalid-color fallback from that commit's universal hover rule. The custom
`.v2-scroll` thumb from R4-T3-02 was not visibly triggered in any of these 26 static
captures (no pane scrolled far enough to show a thumb) — that finding rests on the
`theme.css` source, not a live sighting, and stands either way.

**Verdict**: Win98 has visibly improved since `proof-skins-B.md`'s original pass —
the selected-row contrast failure (its one P1) and the disabled-ink treatment are
both genuinely and fully fixed. The other two fixes both landed correctly at the
primitive level (`Pill`/`Select`/`Input` do bevel; four of the originally-sampled
label spots are sentence case) but stop there — a small, findable set of hand-rolled
call sites (the `Button` primitive in every variant, Settings' own search field, and
four more hardcoded-uppercase labels across four different files) never adopted the
fixed primitive and still show the pre-fix look. None of it is unreadable (no new
P1), but the pattern is systemic enough — the same two defect classes recurring in
new call sites — to warrant a proper sweep for remaining hardcoded
`textTransform`/`.toUpperCase()` and un-bevelled bordered controls, not one-off
patches per site. Geometry fundamentals (zero radius, desktop/window split, ASCII
ScoreRing, Switch reskin) remain solid throughout.

## Design brief input — Cobalt vs SaaS sameness

Token-level comparison plus independent confirmation from the two dedicated theme
reviews above (each reviewer wrote their "visual character" paragraph without
seeing the other's, specifically to cross-check this list). Concretely what reads
the same at a glance:

1. **Same blue family for the primary accent.** Cobalt `#2d5be3` vs SaaS `#1d4ed8` —
   both a mid-saturation, mid-lightness blue in the same 15-20° hue band. Applied to
   the identical set of roles in both (primary buttons, links, focus ring, tag-accent,
   ScoreRing "hi" band), so the one color a user's eye anchors on is nearly identical
   between the two skins.
2. **Same corner-radius language.** Both use 8px on fields/controls/cells
   (`--radius-field/-control/-cell:8`) and near-identical 9-10px on cards/menus/modals
   (cobalt 9/9/9, saas 10/10/12) — a gap too small to read as different at normal
   screen distance. Radius is usually the fastest way a user distinguishes two
   "rounded" themes, and here it doesn't.
3. **Same caps-label treatment.** Both: `.06em` tracking, uppercase, 600-700 weight
   section headers/labels — a 100-weight difference that reads identically at
   10-11px.
4. **Same typographic register**, different files: Cobalt loads IBM Plex Sans, SaaS
   loads the system-ui/Segoe/Helvetica stack — both are clean grotesque sans faces
   with similar x-height and no serif/mono anywhere in a heading slot, so the "voice"
   of the two themes reads the same even though the font files differ.
5. **Same "filled tile" rail-active silhouette** (vs. default/board's thin left bar or
   win98's flat navy fill spanning the row) — cobalt's tile is a fixed dark navy
   `#2c3442`, saas's is the live accent color, but both render as a rounded, inset,
   colored block behind the active nav item at the same `0 10px` inset.
6. **Same "no bevel, soft/no elevation" bucket.** Neither theme touches
   `--bevel-*` (both `none`); cobalt's shadow is a colored soft glow, saas's is a
   neutral soft glow, but both sit in the same "modern SaaS elevation" visual
   register, clearly apart from win98's raw bevels or default/board's flat paper
   cards.
7. **Both ScoreRing variants are non-circular, compact numeral badges** (cobalt: pill
   40×44 tile; saas: bar, numeral + 32×3 track) — different literal shape, same "not a
   ring, a small mono-numeral badge" silhouette at row scale in Feed, where most users
   actually look at it.
8. **Neither customizes the disabled state** — both fall through to `--muted` for
   `--disabled-ink`, same as default; no skin-specific "this control is off" signal.

The one genuine geometric difference a user could spot side by side — cobalt's
**square selected row** (radius 0, `#eef3fe` wash + inset 3px accent edge) vs saas's
**rounded selected row** (radius 8, plain `--accent-soft` wash, no edge) — is confirmed
against the actual screenshots: both dedicated reviews independently verified their
own theme's row-selection shape (cobalt: "hard-edged, square-cornered wash with a
crisp accent bar"; saas: "rounded accent-soft wash, no left edge accent bar"). It is
the single most reliable visual tell between the two skins — everything else in the
sameness list above reads the same at a glance.

## Method notes

- Captures: `docker compose exec backend` running `v2-testing/tools/shots.py T3_<theme>
  --theme <theme>` for each of default/board/cobalt/saas/win98 (52 shots each — 13
  routes × light/dark × 1440/1024), copied to
  `v2-testing/artifacts/round4/t3/<theme>/`.
- Browsers: Firefox 132 and WebKit 2092 installed via `python -m playwright install
  firefox webkit`; `install-deps` failed (Debian trixie package names don't match the
  ubuntu20.04-fallback dependency list) but the individual packages resolved under
  their trixie-equivalent names (`libgtk-3-0t64`, `libicu76`, `libvpx9`, …) except the
  exact old sonames WebKit needs (`libicudata.so.66`, `libjpeg.so.8`) which trixie no
  longer ships under any package name — WebKit could not be launched. Firefox worked
  after that same package pass.
- PDFs: fetched via the live API with `X-API-Key`, rendered to PNG with PyMuPDF
  (`fitz`), reviewed page-by-page.
- Contrast: `contrast.py` (scratchpad) parses `theme.css`, replicates the real
  cascade per `(theme, appearance)`, resolves `var()` chains, computes WCAG ratios.
- Scheduler paused for the capture window (`scrape_interval_minutes`/
  `email_check_interval_minutes` set to 0) and restored to 3500/180 afterward,
  verified with a GET.
