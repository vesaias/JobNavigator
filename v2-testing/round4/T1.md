## Findings — dedup / URL normalisation

The property under test: 20 spellings of one Greenhouse posting must collapse onto one
`external_id`. **16 of 20 do; the 20 fan out to 5 distinct ids.** Three causes account for
the four that diverge (01–03 below); the twentieth spelling, "everything", combines all three.

Groups measured (`test_r4_dedup.py::test_current_spelling_fanout_is_bounded` guards the 5):

```
5f70f284  plain, scheme-upper, host-upper, path-upper, fragment, fragment-and-slash,
          utm-source, utm-bundle, fbclid, gclid, gh_src, mixed-tracking,
          apply-suffix, application-suffix, thanks-suffix, apply-suffix-upper   (16)
0d46f178  trailing-slash        → https://boards.greenhouse.io/acme/jobs/4012345/
2853f580  www-prefix
04af118b  http-scheme
a76df835  everything (http + www + trailing slash)
```

Identity params all behave: Indeed `jk`/`vjk`, Glassdoor `jl`, Dice/Monster `jobId` and
LinkedIn `currentJobId` survive normalisation (and `currentJobId` is correctly dropped on
`/jobs/view/<id>`, where the id is already in the path); the host match is strict, so
`indeed.com.evil.net` gets no identity protection. Ten Indeed postings still yield ten ids.

### R4-T1-01 · P2 · Trailing slash mints a second job row
`_normalize_url()` strips `/apply`, `/application`, `/thanks` and the fragment, but not a
bare trailing slash, so `…/jobs/4012345` and `…/jobs/4012345/` hash differently. Any board
that links a job with and without the slash (or a scraper that joins a base URL with a
trailing separator) creates a duplicate that no later pass can merge — `content_hash`
only catches it when company+title match exactly.
Repro: `make_external_id("Acme","PM","https://x.com/jobs/1") != make_external_id("Acme","PM","https://x.com/jobs/1/")`.
Test: `test_r4_dedup.py::test_trailing_slash_is_the_same_posting`, and the whole-property
`::test_all_twenty_spellings_share_one_external_id`.
**Status**: needs decision

### R4-T1-02 · P3 · `www.` and the bare host are different postings
`_canonical_for_hash()` lowercases the netloc but does not fold a leading `www.`.
`https://www.example.com/jobs/1` and `https://example.com/jobs/1` are two rows.
Test: `test_r4_dedup.py::test_www_prefix_is_the_same_host`.
**Status**: needs decision

### R4-T1-03 · P3 · `http://` and `https://` are different postings
The scheme is part of the canonical string. A board that used to link `http://` and now
links `https://` re-imports its whole catalogue once. (`Rippling`'s seeded URL in `seed.py`
is `http://ats.rippling.com/...`, so this is not hypothetical.)
Test: `test_r4_dedup.py::test_http_and_https_are_the_same_posting`.
**Status**: needs decision

### R4-T1-04 · P3 · Query params are not sorted, despite the comment saying they are
`_normalize_url()` carries the comment *"Sort params for stable hashing"* immediately above
`urlencode(cleaned, doseq=True)`, which preserves `parse_qs` insertion order. So
`?gh_jid=9&location=us` and `?location=us&gh_jid=9` hash differently. It only bites boards
whose functional params survive the tracking filter (Greenhouse `gh_jid`, Indeed `jk`
combined with anything else), but there the duplicate is silent.
Test: `test_r4_dedup.py::test_query_param_order_does_not_change_the_id`.
**Status**: needs decision

### R4-T1-05 · P4 · Percent-encoded unreserved characters are not normalised
`/jobs/senior%2Dpm` and `/jobs/senior-pm` are the same resource per RFC 3986 §6.2.2.2 but
hash differently.
Test: `test_r4_dedup.py::test_percent_encoded_unreserved_chars_are_equivalent`.
**Status**: needs decision

### R4-T1-06 · P4 · `content_hash` does not collapse internal whitespace
`make_content_hash()` lowercases and strips the ends, so `"Senior  PM"` (double space, a
common artefact of HTML-derived titles) does not merge with `"Senior PM"`. Cross-source
dedup is exactly the case this hash exists for.
Test: `test_r4_dedup.py::test_content_hash_collapses_internal_whitespace`.
**Status**: needs decision

## Findings — numeric and type edges on the HTTP surface

### R4-T1-07 · P2 · A negative `limit` is a 500 on every listing endpoint
`/api/jobs` declares `limit: int = Query(50, le=200)` with no lower bound; the other
listings take a plain `int`. Postgres rejects `LIMIT -5`
(`InvalidRowCountInLimitClause` → SQLAlchemy `DataError`), the `DataError` handler sees a
message that is not a uuid error, and answers `{"detail":"Internal server error"}`.
Confirmed live on **seven** endpoints:
`/api/jobs?limit=-5`, `/api/jobs/unscored-ids?limit=-5`, `/api/monitor/history?limit=-5`,
`/api/monitor/finished?limit=-5`, `/api/activity-log?limit=-3`, `/api/scrape-log?limit=-3`,
`/api/applications?limit=-3`. (`offset` is already clamped with `max(0, offset)`.)
Correct behaviour: 422, the same as `limit=abc` gets today.
Tests: `test_r4_live_contract.py::test_negative_limit_is_rejected_not_a_500` (7 params),
plus SQLite-side pins in `test_r4_contract_jobs.py`, `..._applications.py`, `..._system.py`.
**Status**: needs decision

### R4-T1-08 · P3 · `/api/stats/timeline?days=999999999` escapes as an untyped 500

the bare Starlette body `Internal Server Error` (not even the JSON shape the rest of the
API uses). `days=-5` is harmless (empty result).
Tests: `test_r4_live_contract.py::test_timeline_rejects_an_out_of_range_day_count`,
`test_r4_contract_system.py::test_timeline_rejects_an_out_of_range_day_count`.
**Status**: needs decision

### R4-T1-09 · P3 · A malformed uuid in a *filter* answers 404 "Not found"
`GET /api/jobs?search_id=abc` and `GET /api/cover-letters?job_id=abc` return
`404 {"detail":"Not found"}` — the `DataError` handler cannot tell a bad path segment from
a bad query value. A list endpoint reporting "Not found" for a bad filter is misleading, and
it is inconsistent with `/api/monitor/finished?job_ids=abc` and
`/api/monitor/in-flight?job_ids=abc`, which drop unparseable ids and return `200 []`/`{}`.
Correct behaviour: 422 for a filter, 404 only for a path segment.
Test: `test_r4_live_contract.py::test_malformed_uuid_in_a_filter_should_be_422`; the current

### R4-T1-10 · P3 · `/api/health/entities?window` accepts 0 and negatives
`window=0` makes `len(recent) < 0` false and `all([])` true, so **every active company and

**Status**: needs decision

### R4-T1-11 · P3 · `PATCH /api/jobs/{id}` writes caller values into typed columns unchecked
The handler copies any key in `{seen, saved, status}` straight onto the model, so
`{"saved": "banana"}` reaches the driver and 500s. `status` is a free `String` column, so
`{"status": "banana"}` is accepted verbatim and silently creates a status the feed cannot

Test: `test_r4_contract_jobs.py::test_patch_job_rejects_a_wrongly_typed_value`.

### R4-T1-12 · P2 · One malformed id aborts the whole bulk update
`POST /api/jobs/bulk-update` documents `{"updated": n, "not_found": [...]}` so the frontend
can reconcile stale selections, but it looks each id up individually — a non-uuid raises
`DataError` mid-loop, so the request answers `404 {"detail":"Not found"}`, the single
`db.commit()` after the loop is never reached, and **every valid id in the batch is
silently dropped too**. The client is told "Not found" without being told which id, so it
cannot self-correct. A stale client-side selection is exactly what produces this.

## Findings — concurrency and run bookkeeping

Everything asked for here holds. `tracked_run` (scheduler) and `launch_background` (manual)
share one `_running` dict, and the second caller on a scope key is refused in both
directions: manual-then-scheduler raises `JobAlreadyRunningError`, which each of the seven
scheduled jobs catches and logs rather than propagating to APScheduler; scheduler-then-manual
answers **409** on all nine trigger endpoints plus `/api/searches/{id}/run`,
`/api/scrape/company/{id}`, `/api/resumes/tailor`, `/api/cover-letters/generate`,
`/api/analyze/{job_id}` and `/api/jobs/linkedin-import`. Different scope keys of one
job type run side by side (two company scrapes, two `analyze_job` runs with different
`cv_ids`). Ten runs across two scopes leave zero in-memory entries and zero `running` rows.
`cleanup_stale_runs()` marks every orphan `running` row `failed` with
`error="Process restarted"`, a `finished_at` and a positive `duration_seconds`; it is
idempotent, safe on an empty table, and the recovered run shows as failed in
`/api/monitor/history`. `/api/monitor/active`, `/api/monitor/in-flight` and
`/api/monitor/finished` all agree with `_running` and with the `JobRun` rows, before and
after completion, and a failure reason stays server-side.

One finding:

### R4-T1-27 · P4 · `cleanup_stale_runs()` does not consult the in-memory monitor
It fails every `running` row unconditionally. Today that is safe because the only caller is
the lifespan, where `_running` is empty by construction. It is a latent trap for any future
caller (a health endpoint, a watchdog, a manual "clear stuck runs" action): a live run would
be marked failed in the DB while `/api/monitor/active` still shows it running.
Test: `test_r4_concurrency.py::test_stale_recovery_should_skip_runs_the_monitor_still_owns`;
the current behaviour and its rationale are recorded in
`::test_stale_recovery_does_not_touch_a_run_that_is_genuinely_live`.
**Status**: needs decision

## Findings — failure injection

Injected `429`, `529`, read timeout and connection reset at `llm_client._dispatch`, an
`invalid_grant` from the Gmail token endpoint, and a dead Telegram (network error, HTTP 500,
timeout). Results:

- **LLM down → the job is left unscored.** `cv_scores` stays empty, `best_cv_score` stays
  `None`, and `score_single_job` returns `"Scoring failed"` for all four fault kinds. A
  malformed `{"scores": null}` response is likewise not persisted. One `llm_call_log` row is
  written per attempt-set with `success=False` and a non-empty `error`.
- **Retry + fallback are exactly as documented.** The primary is tried 4 times, then the
  fallback once; a transient first failure never reaches the fallback; with both providers
  down a single `RuntimeError` names both pairs; with no fallback configured the primary
  error propagates. The `llm_call_log` row names the pair that **answered** (`openai` /
  `fallback-model`), not the one that timed out.
- **Gmail token expiry is not a crash.** `_get_access_token()` returns `""`, `check_emails()`
  returns immediately, and the scheduled run finishes `completed` with
  `"No new replies"`. A genuine network error does mark the run `failed` with the reason on
  the `JobRun` row, frees the scope, and lets APScheduler handle the exception. A 403 on the
  messages list is swallowed for the next tick.
- **Telegram down does not fail anything.** `_send_message()` returns `False` for a network
  error, a timeout and an HTTP 500, and `False` when unconfigured. `check_scrape_health()`
  raises nothing even when the send raises, and `run_all_scrapes()` still finishes
  `completed` with its scrape summary intact. `POST /api/telegram/test` still answers 202 and
  records the failure only in the run history.

One finding:

### R4-T1-28 · P2 · An LLM outage produces a `completed` run
`_score_job_inner` catches the exception and returns `None`; `score_single_job` turns that
into the string `"Scoring failed"`; `launch_background` treats any returned string as a
successful summary. So the `JobRun` row reads `status="completed"`,
`result_summary="Scoring failed"`, `error=None`. `/api/monitor/finished` — which the v2
dashboard uses to decide OK/NOK for an op that just left `/monitor/in-flight` — therefore
reports a provider outage as a success toast, and Stats › Run history shows it green. The
only place the failure is visible as a failure is the `llm_call_log` table.
Test: `test_r4_failure_injection.py::test_llm_failure_marks_the_run_failed_not_completed`;
the current behaviour is recorded in `::test_llm_failure_run_is_visible_in_the_run_history`.
**Status**: needs decision

## Contract behaviour confirmed correct (no finding)

Recorded as passing tests so a future change to any of it shows up as a failure:

- **Auth.** Every `/api/*` route is 401 without a key and 401 with a wrong key; the
  `jn_session` cookie is accepted in place of the header; `/health` and `/cv/{token}` are
  public; a bare `/` still needs a key (the `?cv` bypass is narrow); `GET /api/settings`
  redacts `dashboard_api_key`, `*_api_key`, `*_password`, `*_secret`, `*_session_id` and
  `gmail_refresh_token`, returns `""` (not six bullets) for an unset secret, and the
  redaction placeholder round-trips through `PATCH` without overwriting the stored value.
- **The `DataError` → 404 handler.** A uuid syntax error maps to `404 {"detail":"Not found"}`;
  every other `DataError` maps to `500 {"detail":"Internal server error"}` with the driver
  message stripped. Verified live on ten id routes.
- **Duplicate submits.** A second application for the same posting is `409` carrying the
  existing `application_id`, leaves no half-written job row, and is caught even when the
  second URL only differs by tracking params. A duplicate company name is `409`
  case-insensitively.
- **Settings validation.** Integers reject `"abc"`, `""`, `"1.5"`, `"1e3"`, `"0x10"`,
  `None`, `[]`, `{}`, booleans and negatives; the five `*_cron` keys reject 4-field,
  6-field, `@daily`, `* * * * mars` and non-string values while accepting `""` (disabled);
  all seven provider enums and the four depth/style enums reject unknown values
  case-insensitively; unknown keys reject the **whole batch**, leaving valid keys in it
  unwritten. A failing `configure_scheduler()` is reported as a `warnings` entry on a 200,
  not a 500.
- **Allow-lists hold.** `PATCH` on jobs, applications, searches, companies, résumés and
  cover letters silently drops every key outside its allow-list — `id`, `created_at`,
  `status_transitions`, `last_run_at`, `last_scraped_at` and `company` were all tried and
  none was written. (Settings and Persona are the two that reject unknown keys with 400
  instead; the inconsistency is deliberate per-router and is recorded, not filed.)
- **Deletes orphan rather than cascade where they should.** Deleting a search nulls
  `Job.search_id` and `ScrapeLog.search_id` and keeps the rows; deleting a company nulls
  `ScrapeLog.company_id`; deleting a base résumé cascades to its tailored children;
  deleting an application releases the job back to `saved`. Second delete is 404 in every case.
- **Extension searches are protected.** `DELETE`, `/run` and `/acknowledge` all answer 409
  for both `extension` and `linkedin_extension` modes.
- **Unicode and size.** Emoji + CJK round-trip through job titles, company names, résumé and
  cover-letter names, persona nodes, settings prompts and qa-bank answers. 10 MB bodies were
  sent to nine endpoints (job description, application notes, search term, company notes,
  résumé `json_data`, cover-letter body, persona node, qa-bank answer, scoring rubric) and
  every one answered 200/201 without a 500. A 6 kB query string is fine. A 10 000-id
  bulk-update is fine. An 11 MB PDF import is rejected by the size guard.
- **Wrongly typed query params are already 422** (`min_score=abc`, `remote=maybe`,
  `limit=abc`, `days=abc`, `tier=abc`, `active=maybe`), and unknown filter *values*
  (`status=zzz`, `source=zzz`) correctly return an empty page rather than an error.
- **Long-running triggers.** `/api/llm/models` answers 400 for an unsupported provider, 400
  when no key is configured, 502 (never 500) when the provider rejects the key or the
  network fails, and serves a stale cache with `"stale": true` when it has one.
