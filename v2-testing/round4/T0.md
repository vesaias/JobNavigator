### R4-T0-01 · P3 · Fresh-install migration chain aborts on the first statement and silently no-ops the rest
**Where** `backend/seed.py:626-631` (the `for sql in migrations: try: db.execute(...) except Exception: log.warning(...)` loop, no `db.rollback()` between statements) vs `backend/models/db.py:154` (`cv_scores = Column(JSON, default={})`).
**Repro** `docker compose up` against a brand-new empty Postgres volume (any version of this branch), then read the backend's startup log.
**Actual** SQLAlchemy's `create_all()` creates `jobs.cv_scores` as native Postgres `json` (from `Column(JSON)`). The migrations list later runs `... WHERE jsonb_typeof(cv_scores) = 'object' ...` and `FROM jsonb_each_text(cv_scores)`, both of which only exist for `jsonb`, so this statement throws `psycopg2.errors.UndefinedFunction: function jsonb_typeof(json) does not exist`. Because the whole list shares one `db` session with no rollback on error, that failure poisons the connection's transaction, and every one of the ~13 migration statements after it in the list (status remap, `job_runs` FK fix, `companies.selected_resume_ids` backfill, the `personas` table creation block, `tracer_links` FK, `DROP TABLE cvs`, `scrape_log`/`searches`/`companies` column adds) logs the same generic `WARNING:jobnavigator.seed:Migration skipped: (psycopg2.errors.InFailedSqlTransaction) current transaction is aborted, commands ignored until end of transaction block` instead of running or reporting its own real outcome. This is 100% reproducible on every fresh install (not intermittent) and is invisible on the existing production DB only because that DB's `cv_scores` column happens to physically still be `jsonb` from before the model changed to generic `JSON` — confirmed by `\d jobs` on the production container: `cv_scores | jsonb`, and its logs carry zero `Migration skipped` lines.
**Impact today** Cosmetic/log-noise only: every migration in that poisoned tail is a documented no-op on a schema `create_all()` already built correctly (verified — nothing in the tail is needed on a fresh DB), and `run_seeds()` still completes and the app starts fine. The real risk is forward-looking and silent: any *future* migration appended after this line in the list will never run on a fresh install and will fail the same generic way, and a maintainer scanning these warnings has no way to tell "this is a harmless retroactive fixup" from "this just broke."
**Expected** Either give `cv_scores` (and any other column a migration assumes is `jsonb`) an explicit `::jsonb` cast so the statement works regardless of the driver-declared column type, or `db.rollback()` inside the `except` branch so one bad statement doesn't cascade into masking the rest.
**Status**: needs decision

### R4-T0-02 · P2 · The welcome/onboarding modal is unreachable on the exact install it's meant for
**Where** `frontend/src/App.jsx:120-147` (`showWelcome` seeded only from `sessionStorage.getItem('jn:welcome')`, `showLogin` only flips true on a 401 from the startup `/api/auth/set-session` call) vs `frontend/src/v2/LoginModal.jsx:29-31` (`sessionStorage.setItem('jn:welcome', '1')` is the *only* place that flag is ever set, and only inside a successful sign-in).
**Repro** Fresh install, no `dashboard_api_key` set (the shipped default — open-access "first-run mode" per `backend/main.py`'s own bypass comment). Open `/v2/feed` in a brand-new browser profile with empty `localStorage`.
**Actual** No modal appears at all — reproduced live: `welcome_modal_visible: false`, `login_modal_visible: false` on first load, plain empty Feed underneath. Tracing the code: the startup effect's `POST /api/auth/set-session` with an empty key succeeds (open access accepts it), so `showLogin` never becomes `true`; `showWelcome`'s only source, `sessionStorage['jn:welcome']`, is only ever written by `LoginModal`'s success handler — which never runs because the login modal never appears. The onboarding wizard whose own copy is "Set up AI scoring… Build your résumé… Activate a company… Configure a search" — exactly the four things a new user needs to be told — is gated behind an action (setting a dashboard key) that most fresh installs won't take on their first visit, since the app works with no key at all. Confirmed the *only* way to see it today is to already know to go to Settings → Advanced and set a key yourself, sign out, and sign back in — which is the tutorial's own step 1, so a user has to already know the thing it exists to teach them.
**Expected** Show the welcome overlay on a genuinely fresh session too (e.g. also seed `showWelcome` from "no prior visit recorded" rather than exclusively from a post-login flag), so the open-access first-run path gets the same onboarding as the key-set path.
**Status**: needs decision

## Part B — upgrade from the oldest backup

Oldest restorable dump in `backups/`: `pre_dedup_cleanup_20260418_000349.sql` (18 Apr 2026, plain-SQL `pg_dump`, 34 MB) — older than the next-oldest candidates (`predeploy_revert_20260730_091348.sql`, 30 Jul; `pre_delete_today_20260822_150606.sql`, 22 Aug) and every `.dump` file in the directory (all from Sept 2026). Restored into `jn_fresh`'s Postgres after `DROP SCHEMA public CASCADE; CREATE SCHEMA public;` via `psql -f`, clean run, **zero errors** (verified with `grep -i error` on the full restore log — none). `dashboard_api_key` on the restored row was overwritten to a disposable test value for the walkthrough (the original was a stored, non-empty historical key — not printed anywhere in this report).

Restarted `backend` against the restored data. Startup log: **no migration warnings at all** — every migration statement in the list ran cleanly this time (the restored DB's `cv_scores` is `jsonb`, so the R4-T0-01 trap doesn't trigger here), including a real one-shot data migration firing for the first time: `migrate_h1b_to_visa_cache: seeded 49 companies into visa_cache`. Table count went from the old dump's 12 (`activity_log_v2, applications, companies, cvs, job_runs, jobs, resumes, scrape_log, searches, settings, tracer_click_events, tracer_links`) to the current model's 16 — `create_all()` added `visa_cache`, `interviews`, `llm_call_log`, `cover_letters`, `personas` clean, and the migration list's `DROP TABLE IF EXISTS cvs` removed the retired legacy table. No leftover legacy columns found on inspection.

**Settings**: old dump had 67 keys; current has 87. Diffed by key name — **25 added** (all for features that postdate April: `autofill_*`, `cover_letter_*`, `scoring_llm_*`, `persona_tailor_prompt`, `prep_ask`/`prep_include`, `prompt_caching_enabled`, `tailor_auto_quick_score`, `tailoring_max_concurrent`, `telegram_webhook_secret`, `default_resume_id`, `jobright_session_obtained_at`, `llm_seeded_models`), each filled from `seed.py`'s `DEFAULT_SETTINGS` — no blank/`None` surprises found on any Settings screen. **6 removed** (`ats_domains`, `company_domains`, `default_cv_id`, `llm_base_url`, `llm_fallback_base_url`, `max_jobs_per_scrape`) — all explicitly and intentionally deleted by `cleanup_removed_settings()` (`backend/seed.py:695-711`), each with its own retirement comment in the source (dead code / retired design). Not a bug.

Walked all 9 top-level `/v2` screens, the résumé editor (opened a real April-era base résumé, "PjM"), and all 16 Settings nav sections (`Display, Models, Scoring behavior, Tailoring, Cover letters, Autofill, Interview prep, Email classification, Scheduler, Global exclude, Dedup tracking params, Notifications, Tracked links, Jobright.ai, LinkedIn, Advanced`) with Playwright against the old data (7,992 jobs, 195 applications, 59 companies, 8 résumés). **Zero console errors, zero page errors, zero HTTP ≥ 400 on every single screen** (one benign `console.warning` — `Datadog Browser SDK: No storage available for session` — traced to a third-party job board's own site loaded inside the Feed's job-posting iframe, not JobNavigator's bundle; grepped the built frontend assets for the string and found nothing, confirming it's foreign-page noise Playwright's page-wide console listener also picks up from iframes).
