## Incident — a real search was deleted and restored

While the flows cases were being written, the row-targeting helper walked up from a control
to the **first ancestor whose text mentions the row name**. On `/v2/searches` that ancestor is
the whole list once the name sits far enough up the tree, so index 0 of `[title="More actions"]`
was not the suite's scratch row but the first real one — the user's **`JobSpy`** keyword
search — and its confirm dialog was accepted. The row was restored; verified through the API
after the run: id `34463384-4fd2-4168-b412-06343de9729c`, `name` "JobSpy", `search_mode`
`keyword`, `active` false, `created_at` 2026-03-02T18:56:45.771911Z, `last_run_at` null.

Three guards were added, and the suite now carries them as rules (`e2e/README.md`,
"Safety rules this suite follows"):

1. `_common.row_index()` refuses to return an index unless the ancestor it settled on
   mentions the suite's `ZZE` marker **and none of the other rows' names**; the failure form
   carries what it rejected, and callers must click nothing on it.
2. Before a `ConfirmDialog` is accepted, **the dialog's own text must name the `ZZE` row**.
3. `flows-sweep` runs last and fails the whole run if any `ZZE` row survived anywhere —
   and every row the suite creates is `ZZE`-prefixed and deleted in the same case.

Nothing that costs money or scrapes runs by default: scratch searches are created
`active: false` with `auto_scoring_depth: 'off'`, the scratch résumé with `is_base: false`,
and every outbound call is route-mocked or behind `JN_E2E_LIVE=1`.

## Findings

### R4-E2E-01 · P2 · Escape does not close the welcome modal over the Feed
`case_welcome` — first visit on `/v2/feed`, press Escape: the overlay stays up (it closes on
`/v2/stats`, and the ✕ works on both).

`WelcomeModal` mounts in `App.jsx`, **outside** the v2 shell, and takes Escape through
`ModalPanel` → `useEscape`. Document-level listeners run in registration order and the screen
behind an overlay mounts first, so `JobFeed`'s own `useEscape` — registered unconditionally
whenever no `ConfirmDialog` is up — ran first, called `preventDefault()` even with nothing to
close, and the overlay's handler bailed on `e.defaultPrevented`. Stats has no unconditional
handler, which is why the same key worked there.

Fixed on both sides, so the topmost overlay wins regardless of which screen is behind it:

- `hooks.js` `useEscape(onClose, active, capture)` — a third argument registers the listener
  in the **capture** phase and calls `stopPropagation()`, so it runs before every screen's
  document listener and nothing underneath closes with it. `ui.jsx` `ModalPanel` exposes it as
  `escapeCapture`, and `WelcomeModal` is the one caller (`LoginModal` has no `onClose`, so it
  takes no Escape listener at all — sign-in is not dismissible, by design).
- `JobFeed.jsx` now gates its handler on **having something to close**
  (`menu · rowMenu · headMenu · shortcutsOpen · picker · rescoreJob`, still `&& !confirm`)
  instead of claiming the key to close nothing.

Every other `useEscape` call site was checked and left alone: `Applications` and `Settings`'
model catalog already stand down for their `ConfirmDialog` (`!confirm`), `Stats`, `Settings`'
`CronBox` and `ResumeEditor`'s head menu are gated on their own open flag, and `ModalPanel` /
`Drawer` keep the default bubble phase. Re-verified live: `modals` (six overlays × open /
Escape / scrim click) and `flows-confirm-delete` (Escape cancels the dialog) both pass.

Regression cover: three new `hooks.test.js` cases (capture beats a handler that registered
first; a capture listener stops an overlay underneath from closing too; `capture=false` still
honours a claimed event) and the `welcome` e2e case, which checks Escape over **both** the Feed
and Stats on purpose.

**Status**: fixed (`frontend/src/v2/hooks.js`, `ui.jsx`, `WelcomeModal.jsx`, `JobFeed.jsx`)

### R4-E2E-02 · P2 · The Feed detail pane overflows the viewport by 87 px at 1024
`case_smoke` — `/v2/feed @1024`: `sw=1024 iw=1024 right=1111`, worst element
`DIV.v2-foldbody`. The "Tailor résumé" button, the ⋯ menu and the report band's "Full report"
button all sat off-screen; every other route at both viewports was clean.

`.v2-fold` is a CSS grid (`grid-template-rows: 1fr → 0fr` is what animates the collapse), and a
grid item's automatic minimum is its **min-content** width. The detail header's fixed action
block (~248 px) plus 30 px padding each side gave `.v2-foldbody` a 507 px minimum inside a
420 px pane, and the extra 87 px pushed the document sideways.

Fixed in two parts:

- `theme.css` — `.v2-foldbody { min-width: 0; max-width: 100% }`, so the body can reach the
  pane width and its rows ellipsise (they already carry `minWidth: 0` + `text-overflow`).
- `JobFeed.jsx` — the detail header row gets `flexWrap: 'wrap'` with a 190 px floor on the
  title column and `marginLeft: 'auto'` on the actions. `min-width: 0` alone fits, but it left
  the title column ~117 px: the company name ellipsised to a single letter and the report
  band's résumé name shrank to nothing. With the floor the actions wrap onto their own line at
  1024 and the header reads normally.

Both halves are inert wherever the row still fits. Measured, same page and pinned clock, with
the new rules injected and reverted: **1440 × 900 → 0 changed pixels**, and the rebuilt bundle
is **0 px** against the `R4_1` baseline shot (`artifacts/design/R4_1/v2_feed__light__1440.png`);
1024 × 700 changes 57 955 px, which is the fix. `smoke` now passes 108/108.

**Status**: fixed (`frontend/src/v2/theme.css`, `JobFeed.jsx`)

### R4-E2E-03 · P3 · The migration warning formatter can abandon the rest of the list
`seed.py` `run_migration_statements()` runs each statement in its own `SAVEPOINT` precisely so
one failure cannot silently no-op the tail (R4-T0-01). But the warning it logs on failure
called `sql.split()` on the raw entry, so a **non-string** statement raised `AttributeError`
out of its own `except` block and dropped every statement after it — reintroducing the exact
failure mode the loop exists to prevent.

Unreachable from `run_migrations()` today (it passes a literal list of strings); reachable from
any future caller that passes a `TextClause` or a mistyped entry. `str(sql).split()` in the
formatter makes the skip graceful.

`test_r4_cov_seed.py` pinned the old behaviour with
`pytest.raises(AttributeError, match="split")`; it now asserts the graceful skip — the bad
entry is reported in `failed`, and the statement after it still runs and commits.

**Status**: fixed (`backend/seed.py`, `backend/tests/test_r4_cov_seed.py`)

### R4-E2E-04 · P2 · An autofill template without `{company}` never gets the persona
`routes_autofill.py` `_build_autofill_prompt()` splits the editable `autofill_prompt` at the
first `{company}` so the profile half can be prompt-cached. Each half then substituted only
*its* placeholders: `{persona}` / `{qa_bank}` / `{max_chars}` before the split,
`{company}` / `{position}` / `{question}` / `{max_chars}` after it.

A template written **without** `{company}` takes the `else` branch — everything becomes the
suffix — so `{persona}` and `{qa_bank}` were never expanded and the model was handed the
literal braces: every answer generated from the user's own edited prompt was written with no
profile at all, silently. The same gap hit a `{question}` placed before `{company}`.

Now one `values` map is applied to **both** halves, so no placeholder survives wherever the
split falls; the split still decides only what is cacheable. Sequential `str.replace`, not
`str.format_map`: the shipped template contains a literal `{"answer": …}` JSON envelope that
any `format()` call would choke on.

`test_r4_cov_autofill.py` asserted the broken behaviour verbatim ("pinning current behaviour");
it now asserts the fix, plus two new cases — every placeholder is substituted in both halves,
and a `{question}` before `{company}` is filled too.

**Status**: fixed (`backend/api/routes_autofill.py`, `backend/tests/test_r4_cov_autofill.py`)

### R4-E2E-05 · P3 · `time.js` echoed cron extensions the backend refuses, and refused one it accepts
`CRON_EXTRAS` claimed to cover "`last`, `last sun`, `fri#3`, `?`". Settings validates a saved
cron with `seed.py` `_cron_error()` → `CronTrigger.from_crontab`, and the two disagreed in
both directions. Checked against apscheduler 3.10.4 in the container:

| expression | `_cron_error` | old `time.js` | now |
|---|---|---|---|
| `0 3 last * *` | accepted | echoed | echoed |
| `0 3 lastw * *` | accepted | **invalid** | echoed |
| `0 3 last-5 * *`, `0 3 15,last * *` | accepted | echoed | echoed |
| `0 3 * * fri#3`, `0 3 * * mon#2,fri` | accepted | echoed | echoed |
| `0 3 ? * *` | `Unrecognized expression "?" for field "day"` | **echoed** | invalid |
| `0 3 5w * *` | `Unrecognized expression "5w"` | **echoed** | invalid |
| `0 3 * * last` | `Invalid weekday name "last"` (`last` is day-of-**month**) | **echoed** | invalid |
| `0 3 * * 4#2` | `Unrecognized expression "4#2"` (`#` needs a weekday name) | **echoed** | invalid |
| `0 3 1st * *`, `0 3 3rd * *` | `Unrecognized expression` | invalid | invalid |
| `0 3 * * last sun` | six fields; `from_crontab` wants five | invalid | invalid |

So the comment's `last sun` example was wrong rather than the code: a **spaced** extension is
six fields and `from_crontab` rejects any count but five, which is why the five-field guard
returning `null` first is the right answer for it. Everything else is a code fix: the loose
regex is replaced by a **field-level** test — `CRON_DAY_EXTRA` (`/^last/`, day of month only)
and `CRON_DOW_EXTRA` (`/^[a-z]{3}#/`, day of week only), each applied per comma-separated
token — so the row echoes exactly what the backend would save and calls invalid exactly what it
would bounce. The reasons `from_crontab` gives are recorded in the code comment, and the
checked table at the bottom of `time.js` gains rows 21–25.

`time.test.js` follows: seven expressions asserted as echoed (all `from_crontab`-valid), six
asserted invalid with the backend's reason quoted, and the `last sun` case reworded from a
FINDING to the agreed behaviour. The `cron` e2e case (which drives the real Settings field)
uses none of the changed expressions and still passes 28/28.

**Status**: fixed (`frontend/src/v2/time.js`, `frontend/src/v2/__tests__/time.test.js`)
