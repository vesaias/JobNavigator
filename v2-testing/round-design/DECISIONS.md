Two confirmations: 58 of the 60 cobalt rows also leak in win98, which shares no palette, radius or type scale with cobalt — only "not Public Sans"; and the `--t-*` stops in cobalt and saas are byte-identical to the base block, only win98 rescales. - **D-17 Theme-named selectors for the two rules that must beat an inline style** — **decided: as implemented** (2026-09-05). - **D-20 The fifth cron field is APScheduler's, not cron's** — **decided: Sunday** (2026-09-05). `backend/seed.py`'s default `h1b_cron` is now `0 2 * * sun` (was `0 2 * * 0`, which fires **Monday** here); existing rows are untouched, and no test asserted the old default. The constraint behind it stands: `backend/scheduler.py:73` hands the field to APScheduler as `CronTrigger(day_of_week=parts[4])` and APScheduler numbers weekdays **0 = Monday … 6 = Sunday**, where vixie cron numbers 0 = Sunday. The two shipped presets are therefore written with names (`0 9 * * mon-fri`, `0 8 * * mon`), which mean the same thing in both dialects, and `describeCron` resolves digits APScheduler's way so an expression already in the DB reads back as what it will actually do. Second divergence, same root, still no action: APScheduler **ANDs** day-of-month and day-of-week where vixie cron ORs them — `describeCron`'s `next` ANDs them and the generic sentence says "on day 1 … **and on** Mon" to make that visible. If the project ever wants the app to speak vixie cron, the fix is on the backend (translate before handing the field to APScheduler), not in the helper.
